# Story 1.15: Importar compras via IA (leitura de print/extrato)

## Status

Draft

## Origem

> Story fora da "Ordem de construção" original do plano — pedida diretamente pelo usuário, discutida em conversa (não implementar agora, deixar pronta pra execução futura). Objetivo: em vez de cadastrar compra por compra manualmente, o usuário envia um print (imagem) do extrato do cartão/banco, uma IA multimodal (GPT-4o/OpenAI ou Claude/Anthropic — **decisão de provedor ainda em aberto, ver "Decisão pendente" abaixo**) extrai as transações em formato estruturado, o usuário revisa/edita/marca quais entram, e só então as compras são criadas de verdade — nunca direto, sempre com revisão humana no meio (conclusão da conversa que originou esta story: extração de imagem por IA erra às vezes, criar sem revisão seria arriscado).

## ⚠️ Decisão pendente antes de implementar (não decidir sozinho)

Esta story **não deve começar a ser implementada sem antes confirmar com o usuário**:

1. **Provedor de IA multimodal**: OpenAI (GPT-4o, chave `OPENAI_API_KEY`) ou Anthropic (Claude, chave `ANTHROPIC_API_KEY`)? A conversa que originou esta story concluiu que os dois funcionam tecnicamente — a escolha final (custo, chave que o usuário já tem à mão, preferência) fica pro usuário confirmar quando for executar.
2. Confirmar que o usuário já tem (ou vai providenciar) uma chave de API válida do provedor escolhido antes de começar — sem isso a feature não funciona e não há como testar de verdade.

Isso é consistente com o padrão já usado no projeto (Story 1.10: dependência nova — `sonner` — só foi adicionada depois de confirmação explícita do usuário). Adicionar uma dependência de API paga é uma decisão ainda mais sensível — **não adicionar SDK nem escrever código de chamada real a nenhum provedor até essa confirmação acontecer.**

## Story

**As a** usuário logado (eu ou minha namorada),
**I want** enviar um print do extrato do cartão e ver as transações extraídas automaticamente numa tela de revisão, de onde eu ajusto o que precisar (cartão, categoria, valor, se é compartilhada) e confirmo quais viram compras de verdade,
**so that** eu não precise digitar compra por compra manualmente quando tenho um extrato inteiro pra lançar de uma vez.

## Acceptance Criteria

1. `/purchases/import` (nova rota): tela com upload de imagem (`<input type="file" accept="image/*">`, uma imagem por vez nesta primeira versão — múltiplas imagens/PDF ficam fora de escopo aqui) e um select de **cartão de destino** (obrigatório escolher antes de extrair — o extrato normalmente é de um cartão só, e não é confiável tentar adivinhar o cartão a partir do texto da imagem).
2. `src/lib/actions/import-actions.ts` exporta `extractPurchasesFromImage(imageBase64: string, mimeType: string)`: `requireUser()`, valida tamanho/tipo da imagem (ex. máx. 10MB, `image/png`/`image/jpeg`/`image/webp`), chama a API do provedor de IA escolhido (ver "Decisão pendente") com um prompt estruturado pedindo um array JSON de transações (`{ date: string (ISO), description: string, valueCents: number }[]`), faz `JSON.parse` com tratamento de erro (a IA pode devolver algo fora do formato esperado) e retorna `{ transactions: [...] } | { error: string }` — **nunca escreve no banco** (mesmo espírito da Story 1.9/Simulação: extração é só leitura/preview).
3. Chave de API do provedor lida de variável de ambiente (`OPENAI_API_KEY` ou `ANTHROPIC_API_KEY`, conforme decisão pendente) — nunca hardcoded, nunca exposta ao client. Se a variável não estiver configurada, `extractPurchasesFromImage` retorna erro claro ("Importação por IA não configurada — falta a chave de API no servidor.") em vez de quebrar.
4. Tela de revisão (Client Component): mostra as transações extraídas numa lista/tabela editável — cada linha com data, descrição, valor (via `CurrencyInput`, moeda = a do cartão escolhido no passo 1), categoria (select de `SUPPORTED_CATEGORIES`, default `other`), toggle compartilhada, e um checkbox "incluir" (marcado por padrão, permite descartar linhas que a IA leu errado ou que não são compras reais — ex. saldo, taxa, estorno). Usuário pode editar qualquer campo antes de confirmar.
5. Botão "Confirmar importação": chama uma Server Action que cria, numa única `db.$transaction`, uma `Purchase` (1x, sem parcelamento — extrato já reflete o valor já cobrado/lançado) por linha marcada como "incluir", reaproveitando a mesma lógica de `createPurchase()` (`purchase-actions.ts`, Story 1.4) por linha — **não duplicar** a lógica de criação, chamar a action existente em loop (ou extrair um helper interno compartilhado se fizer mais sentido no momento da implementação).
6. Se a extração falhar (erro de API, JSON inválido, chave ausente) ou não encontrar nenhuma transação, a tela mostra o erro claramente e permite tentar de novo com outra imagem — nunca trava numa tela em branco.
7. Nenhuma migration nova (reaproveita `Purchase`/`PurchaseInstallment` existentes). Nenhuma lógica de negócio nova além da extração em si — mês da fatura, split de centavos, split 50/50 continuam vindo de `createPurchase()` sem alteração.
8. Custo/segurança: nenhuma imagem é persistida no disco/banco além do necessário pra chamada de API (processada em memória, descartada depois do request) — evita acumular dados sensíveis de extrato bancário sem necessidade.

## Dev Notes

### Previous Story Insights

- `createPurchase()` (`purchase-actions.ts`, Story 1.4) é a fonte de verdade da criação de compra — reaproveitar sempre, nunca duplicar `firstInvoiceMonth`/`generateInstallmentMonths`/`splitValue` aqui.
- `simulatePurchase()` (Story 1.9) é o precedente mais próximo de "processar sem gravar, mostrar preview, só gravar após confirmação explícita" — mesmo espírito aqui, adaptado pra múltiplas linhas de uma vez em vez de uma simulação só.
- `SUPPORTED_CATEGORIES` (Story 1.13) e `CurrencyInput` (Story 1.3) são reutilizáveis diretamente na tela de revisão.
- Story 1.10 é o precedente de "dependência nova só entra com confirmação explícita do usuário antes" — mesma regra se aplica aqui, com um agravante: isso é uma dependência de **API paga**, não só uma lib npm gratuita, então a confirmação é ainda mais necessária antes de qualquer código real de integração.
- Este projeto roda 100% local (SQLite, sem deploy), então a chave de API fica no `.env` local do usuário — sem preocupação de gestão de secrets em produção/CI, mas ainda assim nunca deve ser commitada (`.env` já deve estar no `.gitignore` do projeto — confirmar).

### Por que a criação final não usa parcelamento

O extrato de cartão já reflete transações lançadas (geralmente já "acontecidas"), diferente do fluxo normal de `/purchases/new` onde o usuário pode escolher parcelar uma compra nova. Pra manter esta story simples e alinhada ao que uma leitura de extrato realisticamente representa, cada linha importada vira uma `Purchase` de 1x. Se o usuário precisar de uma compra parcelada específica, continua cadastrando manualmente pelo fluxo já existente — não é escopo desta story tentar inferir número de parcelas a partir do texto do extrato (seria adivinhação, indo contra o princípio de não inventar/assumir dados).

### Sobre custo e chamadas de API

Cada import = uma chamada de API por imagem enviada (visão multimodal tem custo por imagem, maior que texto puro). Não há orçamento/limite definido nesta story — se isso importar, é uma configuração a adicionar depois (ex. limite de imports por dia), não inventada aqui sem pedido explícito.
