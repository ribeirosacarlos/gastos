## Story

**As a** usuário logado (eu ou minha namorada),
**I want** categorizar cada compra e gasto fixo (ex. Alimentação, Transporte, Lazer) e poder filtrar as listagens e ver o gasto por categoria no dashboard,
**so that** eu entenda em que estou gastando mais, não só quanto ou em qual cartão.

## Acceptance Criteria

1. `src/lib/categories.ts` (novo arquivo) exporta `SUPPORTED_CATEGORIES: { code: string; label: string }[]` — lista fixa: `food` (Alimentação), `transport` (Transporte), `housing` (Moradia), `leisure` (Lazer), `health` (Saúde), `education` (Educação), `shopping` (Compras), `bills` (Contas/Serviços), `other` (Outros). Mesmo padrão de `SUPPORTED_CURRENCIES` (`lib/money.ts`): string livre no banco (não enum do Prisma), lista centralizada, adicionar categoria nova = editar essa lista, sem migration.
2. `prisma/schema.prisma`: `Purchase` e `FixedExpense` ganham `category String @default("other")`. Nova migration (`npx prisma migrate dev`).
3. `src/lib/validation/schemas.ts`: `purchaseSchema` e `fixedExpenseSchema` ganham `category: z.enum(supportedCategoryCodes)` (mesmo padrão de `currency` no `cardSchema`).
4. Formulários que criam `Purchase` (`/purchases/new`, `quick-add-sheet.tsx`, `/simulate`) e `FixedExpense` (`/fixed-expenses/new`) ganham um select de categoria, default `other`. `createPurchase()`/`createFixedExpense()` não precisam de lógica nova — `category` passa a fazer parte de `parsed.data`, já persistido igual aos outros campos.
5. `/purchases` e `/fixed-expenses` (listagens) aceitam `?category=` na URL (mesmo padrão do `?cardId=` já implementado em `/purchases` — Story pós-1.12) pra filtrar por categoria, com indicação de filtro ativo + link "limpar". Cada item da listagem mostra a categoria (label, não o código).
6. `src/lib/actions/dashboard-actions.ts`: `getMonthlyTimeline()` ganha `byCategory: Record<string, number>` em cada `MonthlyTotal` — soma (com `userShareCents` aplicado) de `PurchaseInstallment` **e** `FixedExpenseInstallment` daquele mês, agrupada por `category` (chave = código da categoria, ex. `"food"`).
7. `/dashboard` ganha uma seção "Por categoria": lista cada categoria usada no período com o percentual do total (mesmo cálculo de percentual do período já usado na legenda do `month-timeline-chart.tsx`, Story 1.11 — reaproveitar o raciocínio, não necessariamente o componente, já que aqui a fonte é `byCategory` agregado de compras + fixos, não por cartão).
8. Validação: nenhuma dependência nova; migration simples (2 colunas com default, sem risco de dado órfão); categoria inválida no filtro da URL (`?category=xyz`) é ignorada silenciosamente (lista completa, sem erro 500).

## Dev Notes

### Previous Story Insights

- `SUPPORTED_CURRENCIES` (`lib/money.ts`) é o modelo exato a seguir pra `SUPPORTED_CATEGORIES` — string livre no banco, lista centralizada, `z.enum` construído a partir dos códigos (`.map(c => c.code) as [string, ...string[]]`), mesmo padrão usado em `cardSchema.currency` e `exchangeRateSchema.currency`.
- Filtro por query param já existe em `/purchases` (`?cardId=`, story pós-1.12) — reaproveitar exatamente esse padrão (`searchParams: Promise<{...}>`, filtro combinável no `where`, aviso de filtro ativo + link "limpar") em vez de inventar um novo.
- `getMonthlyTimeline()` (Story 1.8, estendida na 1.11 com `byCard`) já itera `purchaseInstallments` e `fixedExpenseInstallments` no mesmo loop — `byCategory` é só mais um `addTo()` dentro desse loop já existente, somando os dois tipos juntos (diferente de `byCard`, que só existe pra `Purchase`).
- A legenda com percentual do período do `month-timeline-chart.tsx` (Story 1.11) já resolveu o cálculo "percentual de cada chave sobre o total do período" — reaproveitar esse raciocínio (não necessariamente o componente) pra seção "Por categoria".
- Nenhuma lógica de negócio nova (split 50/50, limite, câmbio) é afetada — categoria é só mais uma dimensão de agrupamento/filtro.

### Por que categoria inválida no filtro não gera erro

Se o usuário editar a URL manualmente (`?category=xyz`) ou uma categoria for removida de `SUPPORTED_CATEGORIES` no futuro mas ainda existir em registros antigos, o filtro deve degradar graciosamente — melhor mostrar a lista completa (ignorando um filtro inválido) do que quebrar a página com erro 500. Mesmo espírito de robustez já usado no `ignoredCurrencies` da Story 1.8.

### Completion Notes List

- **`byCategory` mudou de tipo em relação ao especificado na AC 6/Dev Notes**: em vez de `Record<string, number>`, ficou `Record<string, Record<string, number>>` (categoria → moeda → centavos). Motivo: uma mesma categoria pode ter gastos em moedas diferentes (ex. "lazer" com uma compra em BRL e outra em EUR) — somar os centavos direto sem separar por moeda estaria matematicamente errado (somaria valores de moedas diferentes como se fossem a mesma). O padrão replica exatamente o que `byCard` já fazia de diferente (lá não precisava, porque cada cartão só tem uma moeda). Documentado no próprio tipo em `dashboard-actions.ts`.
- **Validado via script contra o banco real**: compra de R$200 em "food" + gasto fixo de R$1000 em "housing" no mesmo mês → `byCategory` retornou `{food: {BRL: 20000}, housing: {BRL: 100000}}`, soma total bateu exatamente com a soma manual (120000).
- **Filtro `?category=` robusto a valores inválidos**: implementado checando `SUPPORTED_CATEGORIES.some(...)` antes de aplicar o filtro no `where` — categoria inexistente/removida da lista é ignorada silenciosamente (mostra tudo), não filtra pra uma lista vazia.
- **`CategoryFilter` (Client Component novo)**: usa `useSearchParams`/`router.push` pra atualizar `?category=` preservando outros params já na URL (ex. `?cardId=`) — reaproveitável em `/purchases` e `/fixed-expenses` sem duplicar lógica de URL.
- **Seção "Por categoria" no dashboard**: agrega `byCategory` de todos os meses da timeline, converte cada categoria pra BRL via `getCombinedBRLTotal()` (reaproveitado, mesma função da Story 1.8/1.11) e ordena por valor decrescente — mesmo raciocínio de percentual da legenda do `month-timeline-chart.tsx`, mas categoria não teve gráfico dedicado (lista simples é suficiente aqui, evita sobrecarregar visualmente o dashboard que já tem o gráfico por cartão).
- **`npm run build` e `npm run lint` limpos** (0 erros, 0 warnings; mesmo warning conhecido de `middleware.ts`).
- **Validação manual sem navegador, mesma limitação recorrente**: a agregação (`byCategory`) foi testada via script contra o banco real, mas o clique real (selects de categoria nos 4 forms, filtros nas 2 listagens, seção do dashboard) não foi verificado nesta sessão.
