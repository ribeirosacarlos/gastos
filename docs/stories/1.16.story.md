# Story 1.16: Importar compras via Open Finance (conta bancária conectada)

## Status

Draft

## Origem

> Story fora da "Ordem de construção" original do plano — pedida diretamente pelo usuário, que perguntou se os bancos (Nubank, Inter, Santander e outros) disponibilizam API pra puxar compras do cartão automaticamente. Um estudo de mercado foi feito antes de criar esta story (ver seção "Pesquisa de mercado" abaixo) — a conclusão foi que sim, via **Open Finance Brasil**, e que o caminho viável para um projeto pessoal é um agregador certificado (Pluggy), não integração direta com cada banco. Igual à Story 1.15, esta story fica pronta pra execução futura — **não implementar agora**.

## Relação com a Story 1.15

Esta story é um **segundo método de import**, complementar ao da [Story 1.15](1.15.story.md) (upload de print + IA), não uma substituição:

| | Story 1.15 (print + IA) | Story 1.16 (esta) |
|---|---|---|
| Fonte dos dados | Imagem do extrato, lida por IA multimodal | API do Open Finance via Pluggy, com consentimento do usuário |
| Latência | Imediata (usuário tira o print na hora) | Não instantânea — conectores regulados do Open Finance podem levar até 24h pra disponibilizar transações novas |
| Dependência externa | Provedor de IA (OpenAI/Anthropic), pago por chamada | Pluggy — gratuito por tempo indeterminado pra uso pessoal ("Meu Pluggy") |
| Risco de erro | IA pode ler valor/data errado da imagem | Dado vem estruturado do banco, mas mapeamento conta-Pluggy → `Card` local depende do usuário |

Ambas devem convergir pra mesma tela de revisão (lista editável, checkbox "incluir", confirma cria `Purchase` via `createPurchase()`) sempre que fizer sentido técnico — decisão de reaproveitar ou não o componente da 1.15 fica pra quando a implementação começar (não decidir agora, sem ver o estado do código nesse momento).

## Pesquisa de mercado (contexto, não documentação de arquitetura)

> Sem fonte em `docs/architecture/` para isto — é pesquisa de mercado externa feita nesta story, registrada aqui explicitamente para não ser confundida com decisão de arquitetura já validada.

1. **Open Finance Brasil** é a regulação do Banco Central que obriga instituições participantes a expor APIs padronizadas (mesmo formato para todas) de dados de conta e cartão de crédito, mediante consentimento explícito do cliente. Nubank, Inter, Santander, Itaú, Bradesco, Caixa, BB, C6 e outras ~47 instituições participam. A API de cartão de crédito (v2.4.0) inclui transações e faturas.
2. **Não existe "API do Nubank" isolada** — é uma especificação única que todo participante segue. Virar um participante certificado do Open Finance diretamente (certificados PKI, homologação com o BC) é inviável para um projeto pessoal como este.
3. **Caminho viável: agregador certificado.** Pluggy oferece uma API única sobre o Open Finance, cobrindo os bancos citados, com um programa gratuito para uso pessoal ("Meu Pluggy" em `meu.pluggy.ai` + credenciais em `dashboard.pluggy.ai`) — gratuito por tempo indeterminado, sem limite de contas, desde que sejam contas do próprio usuário (uso comercial ou múltiplos CPFs exige plano pago). Retorna transações com data, valor, descrição e tem webhooks para avisar quando novos dados sincronizam.
4. **Não é tempo real.** Para conectores regulados do Open Finance, transações novas podem levar até 24h para ficarem disponíveis — bem diferente da notificação push instantânea do próprio app do banco. A UI desta story não deve prometer "assim que a compra é passada no cartão".
5. **Alternativa descartada: bibliotecas não-oficiais** (ex. `pynubank`) fazem engenharia reversa do app do banco. Desde 2023 o Nubank passou a exigir verificação biométrica no login, quebrando essas bibliotecas, além de violar termos de uso e arriscar bloqueio de conta. Não recomendado, especialmente havendo caminho oficial gratuito.

Fontes consultadas: [Open Finance Brasil — Área do Desenvolvedor](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/17957025), [PRD API de Cartão de Crédito v2.4.0](https://openfinancebrasil.atlassian.net/wiki/spaces/OF/pages/1739325456/Documento+de+Requisito+do+Produto+PRD+-+API+de+Cart+o+de+Cr+dito+v2.4.0), [Pluggy — Open Finance](https://www.pluggy.ai/open-finance), [Meu Pluggy](https://www.pluggy.ai/meu-pluggy), [Pluggy — API de extrato bancário para ERPs (2026)](https://www.pluggy.ai/blog/api-extrato-bancario-erp-sistema-gestao), [TecnoSpeed — Open Finance Brasil 2026](https://blog.tecnospeed.com.br/open-finance-brasil/), [pynubank (GitHub)](https://github.com/andreroggeri/pynubank).

## ⚠️ Decisão pendente antes de implementar (não decidir sozinho)

Esta story **não deve começar a ser implementada sem antes confirmar com o usuário**:

1. **Cadastro na Pluggy**: o usuário precisa criar conta em `meu.pluggy.ai`, conectar os cartões/contas que quer importar, e gerar `Client ID`/`Client Secret` em `dashboard.pluggy.ai` antes de qualquer código de integração real ser escrito — sem isso não há como testar de verdade (mesmo padrão da Story 1.15/Task 0 com a chave de IA).
2. **Quais bancos/contas conectar primeiro**: não assumir "todos os cartões" — confirmar com o usuário o escopo inicial (provavelmente os cartões já cadastrados no app, um de cada vez).
3. **Fluxo de sincronização**: sob demanda (botão "sincronizar agora" que busca transações novas) é o modelo mais simples e o recomendado como ponto de partida — webhook/agendamento automático fica fora de escopo desta primeira versão, a menos que o usuário quEira o contrário confirmado explicitamente na hora da implementação.
4. **Reaproveitamento de UI da Story 1.15**: se a 1.15 já estiver implementada nesse momento, decidir junto com o usuário se a tela de revisão é compartilhada entre os dois métodos de import ou duplicada — não decidir isso agora, sem ver o estado real do código.

Isso é consistente com o padrão já usado no projeto (Story 1.10: dependência nova só entra após confirmação explícita; Story 1.15: dependência de API paga/externa exige confirmação extra antes de qualquer SDK real). Aqui o agravante é diferente: a API é gratuita para uso pessoal, mas ainda assim envolve uma conta externa (Pluggy) e credenciais que o usuário precisa provisionar — **não adicionar SDK nem escrever código de chamada real à API da Pluggy até essa confirmação acontecer.**

## Story

**As a** usuário logado (eu ou minha namorada),
**I want** conectar meus cartões via Open Finance (usando a Pluggy como intermediária) e puxar as transações recentes automaticamente numa tela de revisão,
**so that** eu não precise tirar print nem digitar compra por compra quando quero importar o que já foi lançado no cartão.

## Acceptance Criteria

1. Nova rota (ex.: `/purchases/import-bank`, ou uma aba dentro de `/purchases/import` se a Story 1.15 já existir nesse momento — decisão de implementação) com: seleção do cartão local (`Card`) de destino e, se ainda não conectado, um fluxo de conexão que abre o widget da Pluggy Connect (via connect token gerado no servidor) para o usuário autorizar o acesso à conta/cartão no banco.
2. `src/lib/actions/open-finance-actions.ts` exporta pelo menos: `createConnectToken()` (gera token de conexão para abrir o widget Pluggy Connect, `requireUser()` obrigatório) e `fetchRecentTransactions(itemId: string, accountId: string)` (busca transações recentes via API da Pluggy, retorna `{ transactions: [...] } | { error: string }` — **nunca escreve no banco**, mesmo espírito da Story 1.9/1.15: busca é só leitura/preview).
3. Credenciais `PLUGGY_CLIENT_ID`/`PLUGGY_CLIENT_SECRET` lidas de variável de ambiente, nunca hardcoded nem expostas ao client. Se ausentes, as actions retornam erro claro ("Importação via Open Finance não configurada — falta credencial da Pluggy no servidor.") em vez de quebrar.
4. Mapeamento entre a conta/cartão retornado pela Pluggy (`itemId`/`accountId`) e o `Card` local do app: persistido de alguma forma (ex. campo novo em `Card` ou tabela de vínculo) para permitir re-sincronizar sem repetir a conexão toda vez — decisão de modelagem a confirmar na implementação, mas sem inventar campos além do estritamente necessário para o vínculo.
5. Tela de revisão das transações buscadas: mesma exigência de revisão humana da Story 1.15 (lista editável, valor via `CurrencyInput`, categoria via `SUPPORTED_CATEGORIES`, toggle compartilhada, checkbox "incluir" marcado por padrão) — reaproveitar o componente da 1.15 se já existir, para não duplicar UI.
6. Botão "Confirmar importação": cria, por linha marcada como "incluir", uma `Purchase` de 1x (sem parcelamento — mesma justificativa da Story 1.15: o valor já reflete uma cobrança lançada), reaproveitando `createPurchase()` (`purchase-actions.ts`, Story 1.4) — **não duplicar** a lógica de criação.
7. A UI deixa explícito que a sincronização **não é instantânea** (pode levar até 24h para transações novas aparecerem, conforme a regulação do Open Finance) — nenhum texto que sugira "tempo real" ou "assim que a compra é feita".
8. Erros tratados sem tela em branco: credencial ausente, conexão expirada/precisa de reautenticação (MFA), nenhuma transação nova encontrada, falha de rede/API da Pluggy.
9. Nenhuma migration nova além do necessário para o mapeamento do AC4. Nenhuma lógica de negócio nova além da busca/mapeamento em si — mês da fatura, split de centavos, split 50/50 continuam vindo de `createPurchase()` sem alteração.

## Dev Notes

### Previous Story Insights

- `createPurchase()` (`purchase-actions.ts`, Story 1.4) é a fonte de verdade da criação de compra — reaproveitar sempre, nunca duplicar `firstInvoiceMonth`/`generateInstallmentMonths`/`splitValue` aqui.
- `simulatePurchase()` (Story 1.9) e o fluxo de extração da Story 1.15 são os precedentes mais próximos de "processar sem gravar, mostrar preview, só gravar após confirmação explícita" — mesmo espírito aqui.
- `SUPPORTED_CATEGORIES` (Story 1.13) e `CurrencyInput` (Story 1.3) são reutilizáveis diretamente na tela de revisão, assim como na 1.15.
- Story 1.10 e 1.15 são os precedentes de "dependência nova só entra com confirmação explícita do usuário antes" — mesma regra aqui, com a particularidade de que a Pluggy é gratuita para uso pessoal (diferente da API paga da 1.15), mas ainda assim exige cadastro externo e credenciais.
- Este projeto roda 100% local (SQLite, sem deploy), então as credenciais da Pluggy ficam no `.env` local do usuário — sem preocupação de gestão de secrets em produção/CI, mas ainda assim nunca devem ser commitadas (`.env` já deve estar no `.gitignore`).

### Sobre o modelo de dados do vínculo conta-Pluggy ↔ Card

Não foi decidido nesta story se o vínculo é um campo direto em `Card` (ex. `pluggyItemId`, `pluggyAccountId`) ou uma tabela separada — isso é uma decisão de modelagem de dados a ser tomada com `@data-engineer`/`@architect` no momento da implementação, não inventada aqui. O importante registrado nesta story é que o vínculo **precisa existir** para permitir re-sincronizar sem repetir a conexão a cada import (AC4).

### Sobre custo

Uso pessoal na Pluggy ("Meu Pluggy") é gratuito por tempo indeterminado, sem limite de contas, desde que todas sejam do próprio usuário. Não há orçamento/limite de chamadas definido nesta story — se isso mudar (ex. Pluggy alterar política de preços), é uma configuração a revisitar depois, não antecipada aqui.

### Testing

- Sem infraestrutura de testes automatizados no projeto ainda. Assim como a Story 1.15, esta depende de uma API externa real — não dá pra simular a resposta da Pluggy de forma confiável sem uma conexão real. O teste principal é manual, ponta a ponta, com uma conta real conectada.
